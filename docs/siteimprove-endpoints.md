# Siteimprove endpoints for the prototype

Drawn from the SWS data inventory (Oct 15, 2026) and the prototype plan. "Confirmed" means the path appears in Siteimprove's documentation or client library. "Inferred" means it is a reasoned guess. "Used by SWS" means an earlier SWS Google Apps Script called it successfully against Stanford's account (shared Nov 19); the response shape is known only from the fields that script read. "Fixture" means a real response is saved in `data/fixtures/siteimprove/` (first set Nov 20). "Linked" means the path appears in the `_links` of `GET /sites/{site_id}` for sitesuserguide, so it exists for this site, but its response hasn't been saved yet. **Call every endpoint once and save the real response to `data/fixtures/siteimprove/` before code depends on it.**

## Access

- **Base URL:** `https://api.us.siteimprove.com/v2`. Confirmed by the Nov 20 fixtures: calls succeeded and every `_links` href uses it. This differs from the `https://api.siteimprove.com/v2` and `https://api.eu.siteimprove.com/v2` shown in Siteimprove's documentation. Keep it in one place in the fetch script.
- **Auth:** HTTP Basic, with the API user's email as the username and the API key as the password. The API user has the same permissions as that user has in the platform, so it must have access to sitesuserguide.stanford.edu.
- **Paging:** `page` and `page_size` query parameters. Responses carry `total_items`, `total_pages` and `links.next.href`; follow `links.next` until it's absent. Not every endpoint honors `page_size`: `dci/history` returned all 212 items on one page. History lists come **oldest first**, so the newest points are on the last page.
- **Deep links:** some responses carry `_siteimprove.page_report.href`, a link to that page's report in the Siteimprove web app (`my2.us.siteimprove.com`), for "Open in Siteimprove" (SP-2). Seen on pages with broken links, pages for a broken link, pages for an accessibility issue, and the page inventory. The accessibility issue list itself has none, so links are per page, not per issue. **Siteimprove adds an `impmd=` parameter; WHM strips it on ingestion** (`stripImpmd`, decisions Nov 20). The links work without it for anyone signed in to Siteimprove.
- **API reference:** https://developer.siteimprove.com/api-reference.html. The Swagger UI requires signing in as the API user.

- **Analytics periods:** analytics endpoints take a `period` parameter (Siteimprove API docs, Nov 20). It can be a single day (`YYYYMMDD`), a range with both days included (`YYYYMMDD_YYYYMMDD`), or one of `now`, `today`, `yesterday`, `last_seven_days`, `last_week`, `last_month`, `this_month`, `this_year`, case-insensitive. Whole dates only. The default is the last 7 days.

## Second probe findings (Nov 20)

Saved as `data/fixtures/siteimprove/probe2-*.json`. `impmd` is stripped from links, and the policy list's `created_by` and `edited_by` names are replaced with `[REMOVED]`.

- **Site Target Score history:** `page_size=500` works, so all 453 points arrive in one call. Real values start on 2025-12-17 (98.57); the accessibility score starts on 2025-12-11. Everything before is 0. Month-end values for sitesuserguide: Apr 98.75, May 98.78, Jun 98.63, Jul 98.78, Aug 98.67, Sep 98.22, Oct 97.87, Nov (so far) 98.38.
- **Page views, `period`:** a 30-day range (`20261021_20261119`) works for top pages: 580 pages, home page 501 views. On `analytics/overview/history`, a range of several months returns **one point per month**, and `last_month` returns one point per day. April and May 2026 are 0, so Siteimprove Analytics data for sitesuserguide starts in June. The current month is partial.
- **Broken links in a check:** `check_history/{id}/broken_links` lists 54 links for the Nov 16 check. The same check's `broken_links` field says 65, and `quality_assurance/overview/summary` says 62 right now, so the counts don't agree. Six of the 54 are on all 351 pages (shared footer links and emergency.stanford.edu); the other 48 are on 1 to 4 pages each, mostly old `userguide.sites.stanford.edu` addresses.
- **Pages for a broken link:** `broken_links/{id}/pages` gives `url`, `title`, `broken_links` and `page_views` per page.
- **Pages for an accessibility issue:** `a11y/issue_kinds/confirmed/issues/{rule}/pages` gives `url`, `title` and `occurrences`, but no page views. URLs can carry a query string (`/events/past?page=1`), so normalize before joining (Q-5).
- **Page inventory:** `quality_assurance/inventory/pages` has `page_views`, `page_level`, `first_seen` and `referring_pages`, but **no last-modified date**. Content freshness (SI-17) stays simulated.
- **Search descriptions:** `seov2/issues` has `meta_desc_missing` (73 pages for sitesuserguide), plus `meta_desc_short`, `duplicate_description` and `duplicate_page_title`. There's no history per issue.
- **Policies:** 114 for this site, all with `all_sites: true`. Prefixes include `[QA]`, `[A11y]`, `[SEO]`, `[SWS]`, `[ADMIN]`/`ADMIN:`/`Admin:`, `TEMP:`/`[TEMP]`, unit prefixes (`[SDSS]`, `[VPSA]`, `[SOM]`), and Siteimprove's own unprefixed policies. Two `[QA]`/`[A11y][QA]` policies match all 351 pages, so they come from the template. Matches are under `_links.matches` (`/content`, `/media` or `/documents`, by category).
- **URL forms differ:** Siteimprove Analytics gives the home page as `https://sitesuserguide.stanford.edu` and QA gives `https://sitesuserguide.stanford.edu/`. Both normalize to `/`.

## Rules for the fetch script

- **Never fetch:** `quality_assurance/inventory/personal_id_numbers`, `email_addresses` and `phone_numbers` appear in `_links`. WHM doesn't need them, and personal ID findings are SWS-only (AD-7).
- **SWS-only content:** drop SWS admin policies (for example "Old Analytics Code" and saml link exclusions) and any personal ID number findings (SI-20) before writing published data (AD-7).
- **Joining to traffic:** normalize URLs before joining issue pages to Siteimprove Analytics page views (Q-5). Where a page can't be matched, rank by how often the issue occurs.
- **Retries and failures:** retry with backoff. The SWS script hit HTTP 429 (rate limited) when calling many sites, and spaced its calls out; one live site in the prototype shouldn't, but handle 429 the same way. If a slice fails, keep that section's last good data and record the reason in `status.json`.
- **Score methodology:** scores are Siteimprove's, not Stanford's, except the Site Target Score. Label them accordingly.
